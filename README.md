# Karna

> **不是“帮你续写一句”的聊天框，而是一套面向长期创作、研究与交付的桌面工作空间。**

[官方网站](https://karna-writer-os.xujiakang75.chatgpt.site) · [三分钟入门](https://karna-writer-os.xujiakang75.chatgpt.site/start) · [示例项目](https://karna-writer-os.xujiakang75.chatgpt.site/examples) · [下载最新版](https://github.com/coca-koala4/karna-desktop/releases/latest) · [社区讨论](https://github.com/coca-koala4/karna-desktop/discussions) · [English](README.en.md) · [安全政策](SECURITY.md)

Karna 面向小说、非虚构写作、研究报告、剧本、课程、论文资料整理与内容团队协作。它把对话、项目文件、知识、版本、智能体工作流、技能与外部工具放在同一个桌面环境中，让 AI 从一次性的回答者，变成一个**可检查、可打断、可追溯、可交付**的创作系统。

Karna 基于 Hermes Agent 的成熟运行时能力继续开发，但产品目标已经不同：Hermes 更像通用智能体运行时；Karna 从项目、文档、人物、资料、版本和交付物出发，为文字工作者构建完整的 Writer OS。

> **当前推荐版本：Karna 1.1.0。** `0.17.x` 已撤回，不应继续安装或传播。请始终通过官方 Releases 获取安装器与更新文件。

## 一眼看懂 Karna

```mermaid
flowchart LR
  I[灵感与任务] --> P[Writer OS 项目]
  P --> K[项目知识与资料]
  K --> C[长篇上下文]
  C --> A[单智能体或多智能体流程]
  A --> H{人工确认}
  H -->|继续| V[版本与审校]
  H -->|退回| A
  V --> D[可交付文档]
```

普通聊天产品关注“这一轮说了什么”。Karna 关注的是：

1. 这段内容属于哪个项目、文档和版本？
2. 它引用了哪些资料，事实与设定能否追溯？
3. 哪些步骤可以交给智能体，哪些必须由人确认？
4. 长篇工作中哪些信息必须保留，哪些可以压缩？
5. 最终如何形成可以继续编辑、审阅和交付的成果？

## 1. Writer OS：让创作围绕“项目”而不是“聊天记录”生长

**状态：实验性；核心项目与文档链路已实现，仍在进行发行级验收。**

Writer OS 将一次长期创作拆成项目、文档、知识、上下文、版本和交付物。小说可以拥有角色、地点、时间线、章节与设定；研究写作可以拥有来源、笔记、论证、引用和报告；团队内容可以拥有任务、评审、修订与发布版本。

它解决的是聊天框最难解决的三件事：

- **项目隔离**：一个项目的资料、记忆与工作流不应泄漏到另一个项目。
- **长篇连续性**：人物关系、术语、约束和前文承诺需要跨越许多轮对话继续生效。
- **交付闭环**：结果不仅显示在消息气泡中，还应进入可编辑文档、版本记录和导出流程。

Karna 的项目知识并非把所有文件粗暴塞进提示词。系统会按文档类型、当前任务、来源和预算组织上下文，并尽量保留能影响创作判断的内容。相关能力仍在持续验证，所以我们不会把路线图中的理想指标写成已经实现的事实。

## 2. 长篇上下文：把“记得多”变成“保留得对”

**状态：实验性。**

长篇创作的难点并不是单纯扩大上下文窗口。真正重要的是：哪些设定不可丢、哪些来源必须引用、哪些旧讨论已经被新版本推翻、哪些细节只对当前章节有效。

Karna 的 Context OS 与 Token OS 以“质量优先、预算可见”为目标：

- 在模型调用前组织项目上下文，而不是把所有历史原样堆入；
- 区分事实、设定、来源、草稿、批注与临时讨论；
- 在多智能体流程中控制重复上下文，减少无意义的反复传递；
- 记录预算与使用情况，让节省 Token 不以破坏长篇一致性为代价。

这些能力面向小说伏笔、研究证据链、剧本人物弧光和系列内容风格一致性，而不是只追求某一轮回答看起来“更聪明”。

## 3. 可视化多智能体工作流：把复杂创作过程变成可检查的流程

**状态：实验性；发行版仅内置两个官方模板。**

Karna 将策划、检索、起草、事实核验、风格评审、结构评审与修订拆成清晰节点。你可以看到每一步的输入、输出、状态和失败原因，而不是让一群智能体在后台不可见地“互相讨论”。

新安装只提供：

- **基础写作流程**：5 个节点，适合从目标到初稿的最短闭环；
- **多评审师循环修订**：11 个节点，用结构、事实与风格评审推动迭代。

官方模板是只读发行资源；复制后的工作流属于用户，更新不会覆盖。流程支持人工确认边界：涉及发布、外发、覆盖文件、使用凭据或其他高风险动作时，系统应停下来请求授权。

## 4. Soul、记忆、RAG、Skill、插件与 MCP：各司其职

**状态：混合；请以应用内标记为准。**

Karna 不把所有长期信息都叫作“记忆”：

| 能力 | 负责什么 | 不应该做什么 | 状态 |
|---|---|---|---|
| Soul | 创作原则、偏好、声音与协作方式 | 绕过安全、权限与隐私规则 | 实验性 |
| 项目知识 / RAG | 找到与当前任务相关的来源和项目材料 | 偷偷跨项目检索 | 实验性 |
| 记忆 | 保存经过筛选、可追溯的长期信息 | 无限积累聊天噪声 | 实验性 |
| Skill | 封装可复用的方法和专业步骤 | 携带用户密钥或测试数据 | 稳定基础设施 |
| 插件 | 组合 Skill、MCP 与应用能力 | 未经检查执行任意安装内容 | 实验性 |
| MCP | 连接外部服务与工具 | 用虚假目录或 Emoji 冒充官方服务 | 实验性 |

MCP 目录只展示已核验并本地打包图标的条目。无法确认官方服务、接入文档或图标再分发许可的候选项不会出现在正式目录中；没有官方可分发图标时使用明确标注的 Karna 通用连接器图标。

## 5. Karna 与 Hermes 的产品级差异

我们尊重并感谢 Hermes Agent。Karna 保留其工具调用、技能、MCP、定时任务与网关等优秀基础能力，同时把产品重心转向桌面创作。

| 维度 | Hermes Agent | Karna |
|---|---|---|
| 主要定位 | 通用智能体运行时与 CLI | 桌面优先的 AI 创作工作空间 |
| 核心对象 | 会话、工具、任务 | 项目、文档、知识、版本、交付物 |
| 长篇工作 | 通用记忆与上下文 | 面向文字项目的上下文与预算组织 |
| 多智能体 | 运行时能力 | 可视化流程、人工确认、评审与修订 |
| 数据边界 | 遵循 Hermes 配置 | Karna 独立用户数据，不迁移旧 Hermes 内容 |
| 安装 | 源码/依赖安装路径 | 完整离线、版本化运行时，不在首启克隆源码 |
| 模型授权 | 可使用环境与既有认证 | 新安装默认未配置，必须由用户明确授权 |

Karna 不是对上游 README 换一个名字，也不是把聊天页套进 Electron。它所增加的是面向创作全生命周期的产品层、数据边界、工作流和桌面交互；具体私有实现不在公开发行仓中发布。

## 6. 安全与隐私：默认不替用户作决定

**状态：新版发行硬门禁。**

新的正式包初始状态固定为 `provider: unconfigured`、`model: null`。即使电脑上已经存在 GitHub Copilot 登录、系统环境变量 API Key、旧 Hermes 配置或其他 CLI 凭据，Karna 也不会自动选择或使用它们。

在用户完成模型选择、主动授权并通过连接测试之前：

- 发送与工作流运行保持锁定；
- 不发出模型请求；
- 不读取旧 Hermes/Karna 项目、会话、Soul 或用户工作流；
- 不导入开发机、浏览器或全局 CLI 凭据。

安装包采用严格白名单。测试、日志、源码资料、`.git`、`.venv`、缓存、个人项目、模型配置、API Key 和旧品牌资源一旦出现在发行内容中，构建必须失败。

发现安全问题请阅读 [SECURITY.md](SECURITY.md)，不要在公开 Issue 中粘贴密钥、个人文件或日志全文。

## 7. 安装、更新与数据位置

**状态：可公开体验；当前推荐版本为 Karna 1.1.0。**

新版 Windows 安装器将提供自定义安装目录、默认工作空间、开机自启动和桌面快捷方式选项。离线运行时位于用户选择的安装目录：

```text
<Karna 安装目录>\runtime\versions\<桌面版本>
```

用户数据保存在 `%APPDATA%\Karna`，默认工作空间由用户选择。更新以新版本运行时原子切换，不覆盖用户数据或已有项目。关闭主窗口会隐藏到系统托盘；只有托盘“完全退出”、更新安装、卸载或系统关机才会结束后台进程。

请始终从 [GitHub Releases](https://github.com/coca-koala4/karna-desktop/releases) 获取安装器，不要从聊天附件、网盘镜像或旧 `0.17.x` 链接安装。

## 8. 真实使用场景

### 长篇小说
把人物卡、地点、时间线、伏笔和章节作为项目资产；让不同评审节点检查连续性、结构和语言，再由作者决定是否接受修订。

### 研究型写作
将来源、摘录、观察与论证放进项目知识；起草时保留引用线索，评审时区分“有来源的事实”和“模型生成的推断”。

### 内容团队
把选题、资料、初稿、品牌检查、事实核验和发布前确认组成流程；每一步保留状态和产物，避免任务只存在于群聊里。

### 个人知识与课程
围绕一个长期主题积累材料，利用 Skill 固化方法，用工作流重复执行整理、提纲、讲义与复盘，而不是每次重新解释背景。

## 9. 能力状态与路线图

我们使用三个明确标签：

- **稳定**：通过自动化测试与人工发行验收，可用于正式工作；
- **实验性**：已经可以体验，但接口、数据或交互仍可能变化；
- **规划中**：方向已经确定，但绝不当作已交付功能宣传。

当前重制重点不是增加更多演示功能，而是完成五个基础承诺：完整离线安装、零隐式模型授权、干净首装、全中文正式界面、可信的品牌与包内容。团队协作增强、更丰富的文档编辑器、移动端协同和更多经核验的连接器属于后续路线图。
